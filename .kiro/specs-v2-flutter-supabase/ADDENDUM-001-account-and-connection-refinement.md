# ADDENDUM-001 — Account & Connection Model Refinement

> **Status:** Authoritative. Supersedes any conflicting text in earlier v2 specs.
> **Date:** 2026-05-25
> **Applies to:** all v2 spec folders.

## 1. Why this addendum exists

After the initial v2 spec set was drafted, the product owner refined the account and connection model. The changes are significant enough that several spec files have been rewritten. This document captures the refinement at a single point so future readers understand the intent without diffing every file.

## 2. The refined model (definitive)

### 2.1 Two account types — Patient and Doctor

There are only **two account types** in v2:

| Role | Description |
|---|---|
| **PATIENT** | Owns medication schedules, dose events, prescriptions. Can connect to other Patients (peer / family) and to Doctors. |
| **DOCTOR** | A clinical professional. Can connect to Patients and create prescriptions for them. |

There is **no FAMILY_MEMBER role**. "Family members" are simply other Patient accounts that have established a peer connection.

### 2.2 Connection types

Two kinds of `connections` rows exist, distinguished by the roles of the two profiles involved:

| Connection type | Roles | Symmetry | What it enables |
|---|---|---|---|
| **Doctor↔Patient** | DOCTOR + PATIENT | **Asymmetric**: doctor can create prescriptions for the patient (subject to the patient's `permission_level`); patient does not access doctor's data. | Clinical care. |
| **Patient↔Patient** | PATIENT + PATIENT | **Mutual**: both sides see each other's adherence and get missed-dose alerts on each other. | Family / caregiver support. |

### 2.3 Connection mechanism — QR scan only

All connections are established via **QR scan only**. There is no manual short-code entry, no doctor search-by-name, no email invitation flow.

The QR is generated by one user and scanned by the other in person (or via a shared image). The QR payload includes a one-time token plus the **generator's role**, so the scanning app knows whether to render a "Doctor connection" UI or a "Family connection" UI.

```
QR payload (encoded as deep link):
dastern://connect?token=<10-char>&role=<PATIENT|DOCTOR>&v=1
```

### 2.4 Authentication — three methods (Google OAuth, Telegram OAuth, email/phone + password)

Sign-up is split into **two role-specific paths** (Patient or Doctor). For each path, the user picks **one of three** authentication methods:

- **Continue with Google** — Google native sign-in via the `google_sign_in` plugin, finalized through `supabase.auth.signInWithIdToken(provider: OAuthProvider.google, …)`.
- **Continue with Telegram** — Telegram Login 2.0 OIDC PKCE flow; the code-exchange step runs inside the `auth-telegram` Supabase Edge Function which validates the ID token against Telegram's JWKS and returns a Supabase session.
- **Continue with email/phone + password** — Manual sign-up using `supabase.auth.signUp(email | phone, password, data: {role})`. Phone sign-up requires SMS OTP confirmation.

Sign-in offers the same three methods. Whichever method the user picks, after authentication succeeds the system reads `profiles.role` and routes to the patient or doctor home automatically.

**Apple Sign-In is deferred to the iOS phase.** It can be enabled later without schema changes — the `profiles` row already has the columns to support it.

**Role propagation across methods.** The role chosen at the Welcome page is captured before the auth flow starts and applied at the **first-time bootstrap** step (when `profiles.first_name` is still null):

| Method | Where the chosen role is carried |
|---|---|
| email/phone + password | Sent in `signUp(data: {role})`. The `on_auth_user_created` Postgres trigger reads `raw_user_meta_data->>'role'` and inserts the profile with that role. |
| Google native | Stored client-side in a transient Riverpod provider before `signInWithIdToken`. After auth succeeds, the Flutter app `UPDATE profiles SET role = ... WHERE id = auth.uid() AND first_name IS NULL` (idempotent: only applies for first-time accounts). |
| Telegram OIDC | Sent to the `auth-telegram` Edge Function as part of the request body (`{code, codeVerifier, redirectUri, role}`). The Edge Function applies it on first-time profile creation, ignored for returning users. |

For sign-in (returning user), no role is requested or applied; the existing `profiles.role` is canonical.

External OAuth providers (specifically Apple) remain post-MVP for v2. Google and Telegram **are** in MVP scope per this addendum.

### 2.4.1 Minimal registration — no enforced professional info for doctors

**Important:** v2 does **not** require doctors to provide license number, license photo, hospital/clinic, or specialty at registration time. The same minimal bootstrap applies to both Patients and Doctors after sign-up:

- **Required:** full name.
- **Optional, defer-able:** date of birth, gender, language preference, timezone.

For Doctors, the professional fields (`hospital_clinic`, `specialty`, `license_number`, `license_photo_url`) are **entirely optional at registration**. The doctor can sign in immediately after providing only their full name and use the app, including connecting to patients via QR.

A separate **"Verify your practice"** screen is reachable later from the doctor's settings (and is surfaced as a non-blocking CTA on the doctor home until completed). When the doctor opts in and submits the professional info, `account_status` transitions from `ACTIVE` to `PENDING_VERIFICATION`; an admin reviews the license photo and sets it to `VERIFIED`.

Effects of verification:
- A `Verified` badge appears on the doctor's profile and on prescriptions they author. This is purely informational — patients can still choose to connect with unverified doctors and accept their prescriptions; the patient remains the data owner and decision-maker.
- Authoring prescriptions is **not** gated by verification status in MVP. The patient's `permission_level` and explicit approval already control what enters their record.

This keeps the registration flow short, lets doctors evaluate the app before committing to verification, and avoids blocking onboarding.

### 2.5 Doctor → Patient prescription flow

Doctors can create medications and send them as a prescription to any patient they are connected to. The patient must explicitly approve the prescription before it becomes ACTIVE.

When approved, the prescription is visible to:
- The patient who owns it.
- The authoring doctor.
- Any **other Patient connected to the patient** (the "family" patients), so they can see what was prescribed and help with adherence.

### 2.6 Mutual missed-dose alerts (Patient↔Patient)

When Patient A misses a dose:
- Patient A receives a missed-dose notification (already in `04-reminder-adherence`).
- **Every Patient B connected to A via a Patient↔Patient connection with `permission_level <> 'NOT_ALLOWED'`** also receives a missed-dose alert.

The alerts are mutual: if B misses a dose, A gets alerted too.

### 2.7 Subscription "family members" disambiguation

The `family_members` table on a Family Premium subscription is **unrelated** to peer Patient connections. It represents the up-to-3 paying members who share a Family Premium plan. The naming is historical; the schema keeps it for clarity inside billing code. The two concepts:

| Concept | Table | Purpose |
|---|---|---|
| Peer-Patient connection ("family connection") | `connections` (PATIENT↔PATIENT row) | Mutual adherence visibility and alerts. |
| Family Premium subscription members | `family_members` (rows under one `subscriptions.id`) | Billing — share one paid subscription across up to 3 users. |

A user can be in either, both, or neither.

## 3. Schema impact

### 3.1 `user_role` enum

Drop `FAMILY_MEMBER`. The enum becomes:

```sql
create type user_role as enum ('PATIENT', 'DOCTOR');
```

A migration removes any existing `FAMILY_MEMBER` rows by promoting them to `PATIENT` (no rows expected in production at MVP).

### 3.2 RLS helper renames and additions

```sql
-- Old (deprecated)
public.is_connected_family_for(p_patient_id uuid)

-- New
public.is_connected_peer_patient_for(p_patient_id uuid)
-- Returns true if auth.uid() is a PATIENT, the target is a PATIENT,
-- and an ACCEPTED connection exists with permission_level <> 'NOT_ALLOWED'.
```

`is_connected_doctor_for` is unchanged.

### 3.3 `connection_tokens.intended_role`

The column type is the new two-value `user_role` enum. Default is `'PATIENT'` (the most common case).

## 5. What is unchanged

- The `connections` table structure (initiator/recipient/permission_level/status) is the same.
- The `permission_level` enum still applies to Doctor↔Patient connections (`NOT_ALLOWED / REQUEST / SELECTED / ALLOWED`) so the patient remains the authority on doctor access.
- For Patient↔Patient connections, only `NOT_ALLOWED` (revoked) and `ALLOWED` (mutual full visibility) are used in MVP. `REQUEST` and `SELECTED` are unused for peer connections (reserved for future granular controls).
- All offline-first, RLS-protected, Supabase-only architectural commitments stand.
- Google Play Billing, OCR pipeline, and all other features are unaffected.

## 6. Migration impact

Because v2 has not shipped, there is no production data to migrate. For any seed or staging data created during pre-MVP development:

```sql
-- Run before applying the new enum migration
update public.profiles set role = 'PATIENT' where role = 'FAMILY_MEMBER';
update public.connection_tokens set intended_role = 'PATIENT' where intended_role = 'FAMILY_MEMBER';
```

After applying:

```sql
alter type user_role rename to user_role__old;
create type user_role as enum ('PATIENT', 'DOCTOR');
alter table public.profiles
  alter column role type user_role using role::text::user_role;
alter table public.connection_tokens
  alter column intended_role type user_role using intended_role::text::user_role;
drop type user_role__old;
```

Apply the same to any other column referencing `user_role`.
